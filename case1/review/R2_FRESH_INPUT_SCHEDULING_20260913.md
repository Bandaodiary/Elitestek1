# R2-C14：保留最新待处理输入的帧调度修复

日期：2026-09-13。范围：独立候选调度器、保留 CNN 与 C13 CPU 适配层的联合验证。

本阶段修复图像年龄问题，不改变模型、数值 golden、MAC 数量、RGBX32 外存布局或 R2V2 寄存器 ABI。C12/C13 源码及已有证据保留。下面区分已经完成的检查与仍运行的验证，不把旧版本的帧率归到新版本。

16:00更新：C14原生六帧已独立完成；四个完整负载间隔最慢15.3145fps@150MHz，六次均选中当时最新完成的帧。第4次的“采集完成→CNN启动”年龄从保留C13的57.81ms降至24.48ms；不是端到端视频延迟或板测，见第5节。

## 1. 问题和可观察影响

C12 六帧原生仿真 `c12_rgbx_xsim_native_sixframe_20260913_a` 中：

| 事件 | 周期 | 原图槽 |
| --- | ---: | --- |
| tag4 采集完成 | 22,285,135 | `0x0C000000` |
| tag5 采集完成 | 27,285,475 | `0x08000000` |
| tag6 开始采集，回收 tag5 | 30,000,023 | `0x08000000` |
| 第四次 CNN 启动，选择剩余 tag4 | 30,956,753 | `0x0C000000` |

旧调度器按槽号挑选可回收 READY，因此即使存在较旧 READY，也可能覆盖最新完成输入。上述时刻本可保留 tag5；选用 tag4 使输入完成到计算启动的年龄多出 5,000,340 拍（按150MHz约33.34ms）。这不是数值错误、原图/结果错配或 CNN 空闲等待问题，不能用 FPS 指标代替它。

## 2. 修复合同

新 `rtl/r2/c1_r2_video_fresh_leases.sv` 的采集分配顺序：

1. 优先真正 FREE 的槽。
2. 没有 FREE 时，优先回收不是 `latest_i_n` 的 READY。
3. 最新帧是唯一 READY 时，仍允许回收它，保证不因这一优化额外阻塞不可回压摄像头。
4. CAPTURING、PROCESSING、PAIR_READY、FRONT 始终不可回收。

使用采集完成事件更新的 `latest_i_n`，不按 tag 数值大小判定新旧，因此 tag 回绕不改变规则。同拍采集完成与新请求使用更新后的状态。原有“完成事件→显示分配→NN分配→采集分配”的优先级、描述符保持、完成屏障及错误处理保留。

这不是“任何负载下都绝不丢最新帧”的承诺，也不是新增队列；它只消除有替代 READY 可回收时不必要的最新帧丢失。
