# 15 fps目标下的架构复核与重构决策

日期：2026-09-12。性质：只读源码/已有运行证据审查及工作量计算；本轮未改生产RTL，
未启动新综合、仿真或板测。分析对象是上一轮最佳性能组合，不是保守默认开关。

## 1. 决策摘要

**建议保留项目基础，重构CNN执行数据通路与调度；不建议继续把当前细粒度执行器的
局部优化作为15 fps主线，也不建议删除整个项目重新开发。**

这不是根据“3.3 fps”外推拍板。确定性证据是：当前模型和计算映射下，原生
640×480单帧理想发射下界为8,928,000拍，而100 MHz/15 fps仅允许6,666,667拍。
即使DDR零等待、控制零空拍，保持当前映射也达不到该频率下的目标。

150或200 MHz下并非数学上绝对不可行，但目标整机频率没有验证；不能把旧版裸核/
窄激励壳的高Fmax移用到目前SoC。100 MHz并非赛题硬性规定，必须将频率视为待验证
设计变量，而不是断言“Ti60本身做不到15 fps”。

## 2. 当前证据究竟说明什么

### 2.1 帧率外推需要纠偏，但数量级警告仍成立

最终对照运行`soc_scalar_assoc_on_64x48_20260912_a`：64×48任务299,189拍，
22层/DDR/显示与独立整数golden一致。将面积乘100得到29,918,900拍，100 MHz下
约3.34 fps；**这不是原生帧率实测，也不包含对物理频率的证明**。

按已有engine FSM记录，逐层配置/参数准备状态1～7合计15,186拍。仅将这部分视作
不随图像面积变化、避免重复放大，得到28,415,486拍、约3.52 fps。这同样只是
敏感性估算：原生行长、突发效率、4 KiB边界和仲裁行为还会变化；不能称为校准结果。
但它说明已知的固定启动开销不会把该粗估自动提升到15 fps。

### 2.2 算术与当前调度的下界

从`model/microstyle_layout.py`和`golden/microstyle_workload.py`重新计算，启用当前
virtual upsample、RGB reduction packing、view elision及final fusion：

| 指标 | 原生640×480 |
| --- | ---: |
| 有效INT8 MAC/帧 | 428,236,800 |
| 15 fps所需有效MAC/s | 6,423,552,000 |
| 当前dot输入发射拍 | 7,564,800 |
| 当前DW窗口发射拍 | 1,190,400 |
| 残差等线性结果拍 | 172,800 |
| 当前逐层串行执行的理想下界 | **8,928,000拍** |

这里下界是每层实际C8映射的dot+DW+linear之和，不是简单将总MAC除64。
MAC是一次乘加，不将其与将乘/加分别计数的GOPS混用。下界忽略访存、量化排空、
输入帧准备、控制和stage切换等实际开销。

| 假设频率 | 15 fps的周期预算 | 当前映射零开销上限 | 判断 |
| --- | ---: | ---: | --- |
| 100 MHz | 6,666,667 | 11.20 fps | 当前计算映射不可能达标 |
| 150 MHz | 10,000,000 | 16.80 fps | 仅余10.72%周期预算容纳全部附加开销 |
| 200 MHz | 13,333,333 | 22.40 fps | 理论可行，但整机频率及实际效率均未证明 |

因此只追求更深缓存、更大outstanding或提高时钟，没有形成可签核的完整方案。

## 3. 四个架构问题

### 3.1 图级工作被拆成过细的张量事务

目前`c1_r1_microstyle_tensor_adapter`以stage为单位切换DDR tensor bank，
`c1_r1_microstyle_engine`共享一个dot路径和一个DW路径。新的列缓存、像素预取、
流水写、连续DW batch确实改善了局部重叠，但还不是连续的整图多层数据流。

`ST_COLLECT`按像素/输入C8组收集，随后切入MAC/DW/线性结果状态；适配层还需
管理窗口请求、响应、结果与写退休。安全的事务屏障本身不应删除，但应该移动到
tile/任务所有权边界，用有界缓冲分离读、算、写，减少其对每个像素的串行限制。

按当前64×48数据将层分组：

| 层类别 | 实际总拍 | 当前理想发射拍 | 比值 |
| --- | ---: | ---: | ---: |
| 普通3×3卷积：0/1/20 | 94,467 | 44,160 | 46.7% |
| 1×1卷积：2/4/6/8/10/12/16/19 | 112,662 | 31,488 | 27.9% |
| DW：3/7/11/15/18 | 58,945 | 11,904 | 20.2% |
| 残差：5/9/13 | 33,069 | 1,728 | 5.2% |

以上比值不是实测DSP占用率；不同FSM/接口的等待有重叠，也不能把所有差额都归为
DDR空等。它们表明瓶颈广泛存在于执行组织，而非只有一个慢模块。

### 3.2 固定8输入×8输出映射不适合所有层

`c1_dot8x8_requant_core`每次发射最多64个乘法，8个输出共享同一输入向量。
末层`output.conv3x3`却只有3个输出通道，因而该层发射时只有3/8输出通道有效。
其原生理想耗时2,764,800拍，占全部8,928,000拍下界的约31%；实际有效MAC只占
全网约15.5%。空闲通道不能靠AXI packing填上。

候选重映射应支持“输出通道×相邻像素”或更长reduction维度，使RGB尾层能利用
更多乘法通路。这需要重做输入bank/广播、累加上下文和结果元数据，不能只改一个
并行度参数；已有8×8核共享输入向量的接口不能直接同时表示两个独立像素。

### 3.3 跨层存储与计算重叠不足

完整特征图常在DDR中物化，DW→PW、PW→Residual等相邻层仍需要跨层读写。
当前存在两种虚拟上采样view及末端identity融合，但不等于网络内部融合已完成。

现有64×48实际tensor通路R/W beat为13,440列读＋1,728标量读＋14,592写，
按相同流量模式放大为47,616,000总线byte/帧、15 fps约714.24 MB/s。这是流量外推，
不是原生总线记录；包括无效WSTRB部分的总线占用，不包含全部捕获/输出/显示等访问。
按用户提供的16-bit、800 Mbps/pin DDR3参数，裸峰值为1.6 GB/s。约45%的裸带宽
尚不能证明DDR一定饱和，但显然不能忽略刷新、读写切换和其他master。

关键不是把所有特征图塞进片上RAM，而是只存可复用的tile、行和部分和，并在合适
的相邻算子间直接传递数据。流式输入归一化也有机会消除一次整帧RGB→C8复制。

### 3.4 模型/图还没有到可以冻结成最终硬件的阶段

当前训练artifact的`artifact_role`明确是
`functional_qat_checkpoint_not_final_quality`，warning明确不宣称比赛画质，
训练说明为六张图、单风格的工程验证。数值对齐通过不能替代艺术效果/多风格验收。

layout仍标注`execution_model=dedicated_multirate_streaming_graph`，其描述符说明
不是逐层DDR执行日程；这是规划元数据，不能据此说当前共享engine已实现该专用图。
当前性能适配又包含固定stage14/17虚拟上采样、stage20/21融合等索引。因此它是一条
已验证的特定网络执行路径，不是对任意CNN都无需重调的通用NPU。

后续应将网络映射变成由算子/形状生成的执行计划，并把模型画质/算量同时作为门槛。
若需要轻量网络，应遵守赛题的真实分辨率/效果要求，不能用更低分辨率推理的fps
冒充640×480结果，也不能跳过重新训练和量化验证。

## 4. 保留与重做的边界

| 资产 | 建议 |
| --- | --- |
| Python整数golden、参数/量化语义、真实图像与错误注入资产 | 保留，作为新路径的独立参考；性能计数合同按新架构更新 |
| ISP/Resize/Gamma、framebuffer所有权、APB/任务控制及CPU接口基础 | 保留，仍须完成官方IP/整板资源与物理集成 |
| AXI事务层、burst reader/writer、取消/排空协议 | 保留可复用实现与测试；重新评估连接、容量和QoS，不保证原连接原封不动 |
| MAC/累加/rounding/saturation的数值实现 | 保留正确性参考；乘法阵列形状、量化共享和端口组织需要重新设计评估 |
| 当前tensor adapter与engine的像素级调度 | 作为旧基线冻结；新高速路径重点替换/重构 |
| 针对固定stage的性能分支和图日程 | 由算子/形状驱动的tile/融合计划取代，避免不断增加特例 |

尽量维持外部寄存器/任务接口，将变化集中于CNN内部命令和数据流。现有工程应
保留作回归基线，不删除源码、旧证据或已经验证的协议边界。

## 5. 候选方案与必须先做的可行性门槛

优先评估**有界tile/行缓冲＋独立load/compute/store调度＋弹性INT8计算阵列**，
并对DW→PW、残差、解码尾部做适度流式融合。权重和部分和尽量局部保留，缓冲
乒乓后才允许下一tile覆写；取消仍排空真实AXI，旧输出不能成为新帧。

两种方案都应参与评估，而不是未验证就锁定一个大重写：

1. 共享/半共享的96或128条逻辑INT8乘法通路：从总MAC的乐观算术预算看，分别
   需4,460,800或3,345,600拍/帧。在100 MHz/15 fps下，需要全帧平均有效通路利用率
   至少66.9%或50.2%。这是候选门槛，不是新架构已有的fps；必须计入padding、
   DW映射、量化、存储端口与所有停顿。
2. 更多层级专用流水：按各层实际速率分配小阵列，而不是每层复制完整8×8核。
   本网络所有3×3层未压缩的两行INT8有效payload合计103,680 B，尚未计C8填充、
   skip延迟、权重、参数、FIFO和M10K端口碎片；因此并非数学上绝对放不下，也不能
   宣称直接可用。需要与CPU/视频IP共同预算，其图特化和资源风险更高。

Ti60器件为160个DSP、256个10-Kbit memory blocks，来源：
[Efinix Ti60规格](https://www.efinixinc.com/shop/ti60.php)。Titanium的Dual模式支持
一条11×10及一条8×8乘法，存在INT8分形打包机会，但共享控制、signed模式与累加
宽度必须满足条件；不能假定综合器总能自动将乘法器两两打包，来源：
[Efinix DSP说明](https://www.efinixinc.com/blog/blog-2026-dsp.html)。

旧版dot+requant裸核物理PNR占80个DSP，因此不能简单复制两个完整旧核后再叠加
其他模块。旧DW小壳28 DSP受内部激励/裁剪影响，也不是完整DW资源保证。旧窄壳
435 MHz更不能成为当前整机频率承诺；见既有Efinity资源报告。

建议的验证顺序：

1. 先以真实原生形状建立逐层MAC、片上bank/端口、DDR byte、输出周期及CPU/视频
   资源预留预算；确定模型效果是否值得保留当前网络规模。
2. 做能代表低利用率1×1、高算量RGB尾卷积、DW→PW和残差的少量原型。使用640宽
   的条带/tiles、真实数据、首尾边界及背压；证明稳态供数和结果吞吐，再做目标器件
   map/PNR。不要以零权重、常量输入或窄壳裁剪结果代替资源证据。
3. 只有周期预算与目标资源均留有整机余量才展开整网集成。若预算不成立，改变阵列
   映射、融合粒度或模型；无需先把失败方案扩写成另一套完整RTL。
4. 最终仍需原生640×480全帧、多个帧、共享DDR竞争及板级时序/画质验证。仿真保留
   计数和必要错误摘要，不生成大体积波形；Vivado继续使用既有脱离Windows Job的运行器。

即使将stage18～20实际耗时全部消除，64×48整体加速上限也只有约1.56倍
（该段占36.0%）。因此尾部融合适合作为可行性原型，不能冒称单靠它解决约4.5倍差距。

## 6. 对进度判断的修正

此前局部正确性、取消恢复和缓存工作是可复用资产，但“功能与验证较完整”不等于
“高吞吐实现接近完成”。原生性能与资源的架构门槛应更早成为主线。上一答复的
3～6周只能算无充分风险展开的粗估，不能在新架构门槛未通过前当作交付工期。

当前应结束以零碎百分比改善作为主要进展指标的阶段，改用以下结果判断是否值得
继续：**原生周期预算是否达标且有余量、目标器件实际资源/时序是否成立、模型画质
是否具备比赛价值。**本报告不宣称新架构已实现或15 fps已可达到。
