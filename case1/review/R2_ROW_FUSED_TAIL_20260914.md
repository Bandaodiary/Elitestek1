## 1. 为什么选择整行融合

[原生阶段剖析](R2_NATIVE_STAGE_PROFILE_20260914.md)显示，全分辨率 DW、PW 和最终 RGB 卷积合计约占已观察作业时间的 36%～37%。这个时间包含 DDR、调度和排空，不是纯 MAC 忙周期；C33 当时仅有少量完整样本，不能当作最终帧率或因果性能对照。

当前候选针对“最近邻 2×视图 → 3×3 DW16 → 1×1 PW16→8”的独占连接。融合保持 DW 与 PW 各自的 INT8 重定标、舍入、饱和及 ReLU，不能把两层乘数合并。Python 匹配按算子、形状和图边进行，不使用固定层号；重命名节点和删除中间残差块的图也已进行模式匹配验证。

先前 6/12/24/48 像素小块实验暴露两个问题：PW 每个输出包推进六个标量，不完整的中间包会破坏现有写回 ABI；频繁重载 DW/PW 参数又可能比省掉的中间结果流量更大。24 像素小块若每块重载参数，每帧额外约 14.93 MB，超过可省的 9.83 MB。共驻权重地址映射虽有软件合同，但不是解决该问题的唯一办法。

**优先实施方案改为：复用现有共享 MAC，在同一缓存中执行完整 DW 行，再执行对应 PW 行，逐行切换现有参数列表。** 相比小块方案，参数切换次数明显减少，并保持原 PW 连续六标量输出次序。

## 2. 现有 16 KiB 内如何容纳两种数据

原 [feature overlay](../rtl/r2/c1_r2_feature_overlay_ram.sv) 有 8 个 512×32 位 SDP RAM 实例。线性视图是两个像素奇偶 bank、每条记录 128 位；空间视图是两个 1024×64 位 bank。

原空间视图选择 `address[9]` 作为半区、`address[8:0]` 作为物理地址。原生 DW16 输入宽度为 320，其逻辑空间地址 0～319 占用了低半区的 320 个地址，无法给 640 像素 PW 输入找到连续 320 条完整线性记录。直接把 PW 基址设为 160 会覆盖 640 个仍有效的 32 位 DW 数据字。

新独立 [partitioned feature RAM](../rtl/r2/c1_r2_partitioned_feature_ram.sv) 改为以 `address[0]` 选择半区、`address[9:1]` 选择物理地址，线性视图不变：

| 原生 640 像素输出宽度 | 物理地址范围，8 个 RAM bank 同时计 | 数据容量 |
| --- | --- | ---: |
| DW 输入空间行 0 | 0～159 | 5,120 B |
| PW 整行中间结果 | 160～479 | 10,240 B |
| 余量 | 480～511 | 1,024 B |

宽度 W 为 4 的倍数且不大于 640 时，保护区为 W/4 条物理记录，PW 基址为 W/4、长度 W/2、结束地址 3W/4。地址模型穷举了 160 个宽度，证明两种空间布局均一一覆盖相同的 4,096 个物理 32 位位置，并验证新分区无别名破坏。见[地址模型](../golden/r2_tail_row_partition_contract.py)和[实际模型日志](../logs/r2_c35_row_partition_contract_20260914_a.log)。该日志当时早于 RTL 创建，其中 `RTL_implemented=false` 是历史快照。

这只是源码容量和地址推导；尚不能宣称 Efinity 保持原 RAM 数量、时序或最终平台容量。

## 3. DW 输出如何写成 PW 可读的行

新 [DW16 row shadow writer](../rtl/r2/c1_r2_dw16_row_shadow_writer.sv) 接受保留计算接口的 48 位数据、6 位 mask、16 位 index 和 LAST。每个双像素、8 通道组产生三包，mask 分别为 `3f/3f/0f`：

| 包阶段 | 实际 32 位 RAM 写入 | 保留数据 |
| --- | --- | --- |
| 0 | 第一个像素的低 4 通道 | 高 2 字节进入 16 位寄存器 |
| 1 | 补齐第一个像素高 4 通道；写第二个像素低 4 通道 | 无需 RAM 读改写 |
| 2 | 第二个像素高 4 通道 | 忽略两字节非零 padding |

两个通道组分别写每个像素记录的低/高 64 位。每包最多提交两个不同 RAM bank 的 32 位字，所有地址直接落到 PW 行基址加像素对索引。

`write_enable` 代表当前周期取得共享线性写端口；无许可时输入必须保持。tag、mask 或 LAST 不合同时，该包和后续包均不写 RAM，接收器排空至实际 LAST 后报告失败。只有完整正确的最后一包实际写入后才发布 `row_valid`。复位或取消立即撤销本地行所有权，但不会擦除 SRAM；外层控制器必须先取消/排空旧计算请求，才能启动下一行。

## 4. RAM 端口、所有权与必须保留的边界

分区不是增加双读端口。每周期仍只能选择一种读取视图；同视图读/回填和两个写入源同时占用仍被断言拒绝。分区开启时，允许 DW 空间低区读取与 PW 影子高区写入同拍，也允许反方向的跨视图读写。逐端口检查上下界，并要求分区 lease 期间配置保持不变。

分区关闭后的普通路径保留“切换视图前需要回填”的合同。地址重排本身是全空间双射，旧空间读写的逻辑数据应保持不变，但仍需完整算子回归证明。仿真断言不是硬件访问保护；真正的缓存 valid、读者所有权和完整行发布必须由融合行控制器维护。

**额外接入风险：PW 最后一个六标量请求可能访问一个未激活的越界像素 bank。** 保留 [PW feeder](../rtl/r2/c1_r2_pw_overlay_feeder.sv) 的 `even_pixel=issue_pixel+issue_pixel[0]` 会在最后一个奇数像素读下一像素对。640 宽、基址 160 时，该未激活 bank 的地址可能是 480，恰好等于分区末端。新 feeder 必须把未激活的末尾 bank 读地址夹到有效行范围，同时保留正确 lane mask；不能仅放宽分区断言或把未知 RAM 字当作有效输入。22:23 已新增独立 feeder 候选，见下文第 8 节，尚未编译验证。独立 RAM/接收器测试本身不覆盖这个 feeder。

[PW 地址合同](../golden/r2_shadow_pw_read_contract.py)进一步穷举 160 个宽度、68,747 次请求和 412,160 个有效输出 lane，检测到 214 次未激活 bank 越界，640 宽的最后两个请求各出现一次。夹取后所有有效 lane 的输入地址保持正确、不触及 DW 低分区。[b 日志](../logs/r2_c35_pw_shadow_read_contract_20260914_b.log)是软件模型证据；a 在源码前提检查因把实际 `+6` 误写为字符串 `+16'd6` 而停止，修正的是检查脚本，不是保留 RTL。

## 6. 吞吐和资源预期，不等于结果

640×480、DW 输出 16 通道时，省去一次整帧写回和一次 PW 整帧读入，推导流量为 `2×640×480×16 = 9,830,400 B/frame`。两组参数列表合计 72 个 128 位 beat；由各读一次改为每行重载，额外 `479×72×16 = 551,808 B/frame`。净减少 **9,278,592 B/frame**。

这不包含新增调度等待、可能变化的缓存回填和实际 DDR 争用，不能换算成已实现 fps。共驻 DW/PW 权重可作为后续优化，但第一版整行融合不以共驻权重为前置条件。资源目标是复用已有 16 KiB 特征区域和 96 MAC；新增接收器控制逻辑、路由及时序代价必须通过实际 map/PNR 衡量。
